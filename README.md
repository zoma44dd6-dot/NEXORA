# نبض | NABD — منصة المعلومات الصحية

مشروع ويب عربي (RTL) يضم واجهة متجاوبة، موسوعة أمراض قابلة للبحث، قسمًا للأمراض النادرة، دليل أدوية، دليل جهات طبية، مقالات تثقيفية، حسابات مستخدمين، مفضلة، وواجهة إدارة محمية لإضافة المحتوى وتعديله وحذفه. يحتوي المشروع على Backend حقيقي مبني بـ Node.js وExpress وملفات بيانات قابلة للتطوير.

> **تنبيه مهم:** هذا مشروع برمجي قابل للتشغيل، لكنه ليس اعتمادًا طبيًا أو منتجًا سريريًا جاهزًا دون مراجعة. بيانات البذرة محدودة وبعضها معلّم بأنه يحتاج مراجعة. لا تستخدمه لاتخاذ قرارات التشخيص أو العلاج، ولا تعلن أن جهة تقدم علاجًا معينًا قبل التحقق منها. يلزم مراجعة طبيب/صيدلي مختص ومصادر رسمية قبل الإطلاق العام.

## 1. المتطلبات
- Node.js 20 أو أحدث.
- npm.
- استضافة تدعم تشغيل خادم Node.js وكتابة تخزين دائم للبيانات. **GitHub Pages وحده لا يشغّل الـBackend**.

## 2. التشغيل محليًا

```bash
npm install
cp .env.example .env
```

افتح `.env` وغيّر `JWT_SECRET` إلى قيمة عشوائية طويلة، وغيّر `ADMIN_EMAIL` و`ADMIN_PASSWORD` إلى بيانات قوية وفريدة. لا ترفع `.env` إلى GitHub.

```bash
npm start
```

ثم افتح `http://localhost:3000`.

على Windows، انسخ `.env.example` يدويًا إلى ملف اسمه `.env` بدل أمر `cp` إذا لم يكن متاحًا.

## 3. بيانات الإدارة
- يقرأ الخادم `ADMIN_EMAIL` و`ADMIN_PASSWORD` من متغيرات البيئة.
- القيم الافتراضية مخصصة للتطوير المحلي فقط: `admin@nabd.local` و`ChangeThisPassword123!`.
- **غيّرها قبل أي نشر.** في الاستضافة، أضف المتغيرات من لوحة إعدادات الخدمة ولا تضع الأسرار داخل ملفات المشروع.
- افتح «بوابة الإدارة» أسفل الصفحة، ثم سجّل الدخول. يمكن إضافة مرض أو دواء أو مستشفى أو مقال. كل المحتوى الجديد يُعلّم `needs-review` حتى يراجعه مختص.

## 4. النشر على GitHub والاستضافة
1. أنشئ مستودع GitHub جديدًا.
2. ارفع محتويات هذا المجلد إلى جذر المستودع، وليس ملف ZIP نفسه.
3. أنشئ خدمة Web Service على استضافة تدعم Node.js (مثل Render أو Railway أو خادمك الخاص).
4. أمر البناء: `npm install`، وأمر التشغيل: `npm start`.
5. أضف `JWT_SECRET` و`ADMIN_EMAIL` و`ADMIN_PASSWORD` كمتغيرات بيئة سرية.
6. اربط تخزينًا دائمًا بمجلد `data/`؛ لأن `data/store.json` هو التخزين الحالي، وقد تُفقد التغييرات عند إعادة نشر الخدمة إذا لم يكن التخزين دائمًا.
7. اختبر `/api/health` للتأكد من عمل الخادم.

## 5. نقاط API المتاحة
- `GET /api/health` حالة الخدمة.
- `GET /api/summary` إحصائيات عدد السجلات.
- `GET /api/diseases?q=&category=&rare=` و`GET /api/diseases/:id`.
- `GET /api/drugs?q=`.
- `GET /api/hospitals?q=&governorate=`.
- `GET /api/articles`.
- `POST /api/auth/register` و`POST /api/auth/login`.
- `GET /api/me` و`GET /api/me/favorites` و`POST /api/me/favorites/:diseaseId`.
- مسارات الإدارة: `GET /api/admin/content` و`POST/PATCH/DELETE /api/admin/:collection[/:id]` مع رمز إدارة صالح.

## 6. التخزين وحدود النسخة الحالية
البيانات في `data/store.json` بصيغة JSON لتسهيل البدء. هذا مناسب للنموذج الأولي ولحجم صغير، لكنه **ليس قاعدة بيانات إنتاجية مثالية**. قبل التوسع الفعلي، انقل البيانات إلى PostgreSQL أو قاعدة مُدارة، أضف ترحيلات schema، نسخًا احتياطيًا، واختبارات استعادة.

حاليًا تسجيل الحساب يدعم البريد وكلمة مرور مشفرة بـbcrypt، لكن النظام لا يحتوي على تحقق بالبريد أو استعادة كلمة المرور أو MFA. لا تخزن تقارير طبية حقيقية أو بيانات صحية حساسة في هذا الإصدار قبل مراجعة أمنية وقانونية كاملة. لا يُسمح برفع الملفات الطبية في هذه النسخة.

## 7. قبل الإطلاق العام (قائمة إلزامية)
- مراجعة كل صفحة مرض وكل معلومة دوائية بواسطة مختص مؤهل.
- إضافة المصادر الدقيقة وتاريخ المراجعة واسم/صفة المراجع.
- التحقق من بيانات المستشفيات والخدمات وأرقام التواصل دوريًا.
- استبدال التخزين JSON بقاعدة بيانات مُدارة مع نسخ احتياطي.
- إضافة اختبارات آلية ويدوية، ومراقبة أخطاء، وسياسة خصوصية وشروط استخدام.
- إجراء اختبار اختراق ومراجعة صلاحيات الإدارة والجلسات وحماية البيانات.
- مراجعة المتطلبات القانونية والتنظيمية المصرية ذات الصلة قبل جمع بيانات المرضى أو تقديم خدمات صحية.
- عدم تقديم تشخيص آلي أو توصية علاجية شخصية دون تصميم سريري ومراجعة وتنظيم مناسب.
